# 11：从训练历史构建500个LLM用户画像

## 这一章的开发流程与经验

先固定模拟用户及其证据，再生成画像，最后验证并缓存。画像不是点击行为：本章只创建后续点击评价的输入，不改现有 A/B 环境和采纳条件。

1. 统计历史充足的训练用户，固定抽样及随机种子。
2. 用训练词表映射电影标题、上映日期和类型。
3. 取近期正反馈，明确不知道不喜欢什么，也没有真实曝光。
4. 用同一提示词批量总结，并要求可核对的电影引用。
5. 校验后逐人保存，记录输入与模型版本，失败可恢复。

经验：生成可读的画像容易，确保它没有引用错误用户或错误电影更重要。LLM总结是偏好假设；证据校验只保证引用存在，不证明用户真的会点击。

## 1. 数据怎样进入画像

入口 `simulation/profiles.py:prepare_profiles` 只读取 manifest、train.csv、id_maps.json 和电影元数据，不读取 validation.csv、test.csv、原始完整评分表或人口属性。

train.csv 中的 item_id 是处理后编号，u.item 中是原电影编号，两者必须通过 item_original_ids 映射。直接把内部编号当原电影编号会读错电影。

从本机已下载的 ml-100k.zip 中提取 u.item、u.genre 两个固定成员，不重下数据，不改变评分划分。元数据按 Latin-1 解码。题材来自原文件，不让模型根据记忆补剧情。

默认选500人，训练正反馈至少20条，每人提供最近20条，抽样seed=42。先按 timestamp、item_id 排序，再取最近历史。当前本地有675人符合要求，固定抽500人，共10000条历史电影记录。没有补采样或复制用户。

```bash
mini-agentx user-profiles --prepare-only
```

准备目录包含 users.json、items.json、prompt.md、status.json、activity.md、profiles/、requests/。目录名称有新加坡时间戳；输入、训练映射及电影元数据记录摘要。

## 2. 用户画像 Agent 需要什么

这个 agent 不需要终端或工具调用，它的任务是从已经准备的事实生成一个结构化结果。

system 是 `SYSTEM_PROMPT`，完整副本保存在本次 prompt.md。它要求：只根据训练正反馈及明确类型总结，不推断人口属性或讨厌的类型，不编造剧情；最多5个偏好，每个最多3部支持电影，并说明不确定性。

user 消息是 users 数组，每人包含：

- user_id：匿名内部编号。
- total_training_positives：完整训练正反馈数量。
- history：最近电影的内部编号、标题、上映日期和类型。
- genre_evidence：程序从这份历史构造的类型与可引用电影ID映射。

最后一个字段帮助模型正确复制证据，不是额外标签或未来交互。一次请求默认10人，通过普通JSON输出，不调用工具。

```json
{
  "profiles": [{
    "user_id": 0,
    "summary": "偏好冒险与科幻题材，但历史仅包含喜欢过的电影。",
    "preferences": [{"genre": "Sci-Fi", "evidence_item_ids": [12, 30]}],
    "uncertainties": ["无法判断不喜欢的类型", "只使用近期训练正反馈"]
  }]
}
```

这是格式示例，ID必须以实际输入为准。输出没有点击概率；概率判断属于下一阶段。

## 3. 校验与修复

validate_profiles 检查用户完整且不重复，字段和文本长度正确，偏好数量合理，支持电影属于这个用户的训练历史，而且电影的真实类型与被引用类型一致。

例如引用《狮子王》证明科幻偏好，类型校验会拒绝，并指出该用户历史中真正具有科幻类型的电影ID。错误返回模型，最多两次尝试；不会偷偷删除错误引用或补成看似成功的画像。

它不验证summary的所有语义，仍要抽查。原请求与返回全部保存在 requests/，不保存认证header或key。

## 4. 缓存与恢复

每个通过校验的画像保存为 profiles/user-NNNN.json，包含画像和 input_sha256。身份由用户输入、核心提示词和配置模型组成。恢复时核对输入文件、提示词和已有画像；不混用不同配置模型，不重新调用已完成用户。

```bash
# 创建新样本并生成，最多100次请求
mini-agentx user-profiles --count 500

# 从已有目录恢复，最多100次新增请求
mini-agentx user-profiles \
  --directory runs/profiles-<时间戳>-<ID> \
  --max-model-calls 100
```

每批10人意味着500人正常需要50次请求，修复会额外计数。max-model-calls 是本次执行的请求预算，status.model_calls 是累计次数。API或校验失败保存状态；再次执行同目录只生成尚未完成的用户。活动日志按用户展示总结、类型和电影标题依据。

## 5. 如何接到后续A/B

后续A/B从同一批500用户中分流，两组共用固定画像。候选电影兴趣评价只看画像和电影信息，不知道来自A或B，也不看模型分数。用户与电影的兴趣概率应缓存，再由程序结合位置产生模拟点击。

本章只实现画像。后续[教程12](12-profile-ab.md)已实现兴趣评价及可选A/B环境；workflow默认仍使用原环境，需要 --ab-config configs/abtest-profiles.toml 切换。

## 6. 验证

`tests/test_user_profiles.py` 验证最新历史排序与内部电影映射、未读取留出交互、画像引用错误拒绝、缓存恢复不重复调用、输入修改拒绝、用户不足时不重复采样。实际500人的画像另由已配置DeepSeek生成，不能用mock结果冒充。
